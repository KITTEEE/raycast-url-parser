  ---
  方案 A — Form 组件（推荐）

  用 Raycast 的 Form 组件实现。URL
  输入框在顶部（自动填入剪贴板），解析后在表单内展示各 URL

  输入对，底部实时预览生成的新 URL。提交即复制。

  优点：原生 Raycast 体验，键盘导航流畅，支持动态增删参数行，代码结构清晰。
  缺点：Form 的样式不如 List 灵活，参数较多时页面会较长。

  ---
  方案 B — List 组件 + Action Panel

  主界面用 List 展示各参数为列表项，选中某项后通过 Action Panel 弹出编辑。URL
  输入框作为搜索栏。

  优点：浏览体验好，适合参数数量多的 URL。
  缺点：编辑路径间接（要打开 Action → 编辑 →
  确认），不够流畅；不符合"直接内联编辑"的需求。

  ---
  方案 C — Detail + 自定义 Markdown 预览

  用 Detail 组件做只读展示，通过 Action Panel 跳转到编辑 Form。

  优点：展示效果最好看。
  缺点：交互跳转多，和你要的"内联编辑"体验有差距。

  ---
  我的推荐是方案 A，Form 组件最契合"逐行编辑 key + value"的需求，也是 Raycast
  生态里最自然的编辑交互。你觉得呢？

  核心状态（React state）：
  - rawUrl — 用户输入的原始 URL 字符串
  - parsed — 解析后的结构体（协议、域名、路径、参数数组、锚点）

  数据流：rawUrl 变化 → 解析 → 填充各字段 / 任意字段修改 → 序列化 → 实时生成新

  ---
  i18n 方案

  Raycast 没有内置 i18n 基础设施，用轻量方案：在 src/i18n/ 下放 en.ts 和 zh.ts
  两个字符串常量文件，运行时通过
  Raycast.environment.textSize（或系统语言）自动选择，英文为默认。所有 UI
  字符串集中管理，不散落在组件里。

  src/
    i18n/
      en.ts    # 英文字符串（默认）
      zh.ts    # 中文字符串
      index.ts # 根据系统语言导出对应 locale

  ---
  边界情况处理清单

  场景: 剪贴板为空 / 非 URL 内容
  处理方式: 显示空输入框，提示用户粘贴 URL
  ────────────────────────────────────────
  场景: URL 格式不合法
  处理方式: 输入框标红 + 错误提示，不解析
  ────────────────────────────────────────
  场景: 无 Query 参数的 URL
  处理方式: 参数区显示空状态 + "Add parameter" 按钮
  ────────────────────────────────────────
  场景: 参数值含编码字符（%20 等）
  处理方式: 自动 decode 后展示，序列化时重新 encode
  ────────────────────────────────────────
  场景: 参数 key 为空
  处理方式: 该行标红，提交时跳过或提示
  ────────────────────────────────────────
  场景: 重复 key
  处理方式: 允许（部分 API 合法使用），不做限制
  ────────────────────────────────────────
  场景: 非 HTTP/HTTPS 协议（ftp、mailto 等）
  处理方式: 尝试解析，不强制限制协议类型
  ────────────────────────────────────────
  场景: 含端口号的 URL（localhost:3000）
  处理方式: 正常解析，端口含在"域名"字段里
  ────────────────────────────────────────
  场景: 超长 URL
  处理方式: 输入框支持滚动，不截断
  ────────────────────────────────────────
  场景: 数组参数（ids[]=1&ids[]=2）
  处理方式: 视为普通 key，不做特殊合并
